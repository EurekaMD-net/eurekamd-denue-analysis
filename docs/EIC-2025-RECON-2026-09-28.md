## 1. Source inventory (INEGI, released 2026-09-22)

Every file downloads with plain curl (no challenge wall on `/contenidos/`).
A missing file still answers HTTP 200 with a 2,263-byte HTML decoy, so any
loader must check the Content-Length / magic bytes, not the status code.
The program page is React-rendered; the files were found through the
page's own listing API:

```
https://www.inegi.org.mx/app/api/descarga/componente/descargamasiva/lista/archivoscompaginacion?tema=0&subtema=0&areaGeografica=<0|EE>&proyecto=0&anio=0&tipodocto=<5 tabulados|4 microdatos|12 datos abiertos>&agrupacion=VG9kYXM=&idBiinegi=3455&desde=1&hasta=1000&textoBuscar=&ordenar=orden&ingles=0&datosAbiertos=0&orden=
```

Open-data CSV facts:

- Geo units: 1 national, 32 entidad, **2,478 municipios** (`CVE_LOC='0000'`),
  32 entidad totals for localities < 50k (`CVE_MUN='997'`, `CVE_LOC='9997'`),
  233 localities ≥ 50k.
- Sentinels: `MI` = sample too small, `NA` = not applicable.
- `NOM_MUN` carries footnote suffixes to strip: `*` = fully enumerated (750:
  747 old keys + 12083/12084/12085), `**` = sample too small (7).
- Absolute counts: POBTOT/FEM/MAS, P_3/5/12/15YMAS, P_6A14, POB0_14,
  POB15_64, POB65_MAS, POCUPADA, PDER_SS, PUSU_SS, TOTHOG, HOGJEF_*, POBHOG,
  VIVPARHAB, OCUPVIVPAR (GRAPROES is an average, mapped directly). ~280
  other columns are percentages
  (`PCN_*`: quinquenal groups, `VPH_*`, PEA, PSINDER, PDER_IMSS/ISSSTE).
- Cross-check: 12001 POBTOT = 767,454 in both the tabulado and the CSV.
- **Universe caveat**: EIC `POBTOT` counts people in occupied private
  dwellings only; Censo 2020 `pobtot` includes collective dwellings
  (12001: 779,566 in 2020 vs 767,454 in EIC). A naive "growth" column mixes
  two universes.

## 3. The live defect this exposes (exists today, before EIC)

DENUE 05/2026 and the other refreshed layers already use the 2025 keys
(`establecimientos.area_geo` is the 5-char key):

| Layer | Rows on the 9 new keys |
| --- | --- |
| `establecimientos` (DENUE 05/2026) | 4,950 (24059 Villa de Pozos alone: 2,320) |
| `ce2024_municipal` | 6,583 |
| `clues` | 70 |
| `mv_delitos_municipal_yearly` | 36 |
| `mv_mortalidad_municipal_yearly` | 6 |
| `sedatu_financing_by_municipio` | 5 |
| `coneval_pobreza_municipal` (2020) | 0 |

Consequences in `src/api/handlers/analytics.ts`:

- `locustMuniSql` (~`:4916`) drives from `censo_municipios` → the 9 areas are
  absent from its output.
- `municipiosSql` (~`:502`) drives from DENUE → they appear with NULL
  `poblacion` and NULL CONEVAL.
- `/municipio-detail?cve_mun=24059` → 404.
- Parents' per-capita figures are skewed: 24028 San Luis Potosí keeps its
  2020 population (911,908, which includes Pozos) while 2,320 of its
  establishments now sit under 24059.

Also seen: stray `area_geo` values in DENUE that exist in neither catalog,
16 codes / 24 rows with 1–4 rows each (08999, 50991, 23014, 25059, …), all
from bogus CLEE prefixes (4 rows sit in another entidad). Fixed by
`scripts/rekey-stray-area-geo.sql` (2026-09-29), which re-keys `area_geo`
and `entidad` from the containing MG 2025 polygon; it is now the
`area_geo_rekey` post-step of `ops/denue-refresh.sh`.

## 4. Loader conventions to follow

- `scripts/load-censo.ts`: all-TEXT staging from the CSV header
  (`:74-112`), `\copy … NULL '*'` (`:140`), explicit `DROP VIEW` of
  dependents then swap (`:141-145`), generated `cve_mun` + indexes
  (`:124-130`), views from `migrate-censo-views.sql`, `postLoadGrants`, all
  in one `runPsqlScript` transaction, then `assertRelationsExist`.
- Typed views over TEXT raw: `NULLIF(NULLIF(col,''),'N/D')::int`
  (`migrate-censo-views.sql:20-25,43-55`). EIC sentinels are `MI`/`NA`;
  strip `*`/`**` from `NOM_MUN`.
- Grants: new `GRANT SELECT ON <view> TO denue_sage;` line in
  `scripts/sage-role.sql`; add the view to the `FOREACH` array in
  `scripts/api-role.sql:56-87`.
- Ledger: `npx tsx scripts/record-dataset-version.ts --dataset=eic_2025 --edition=... --rows=N --apply`.
- Parity fields the handlers read from `censo_municipios`: `pobtot` (22
  uses), `cve_mun` (18), `nom_mun` (7), `pea`, `psinder`, `graproes`,
  `p_12ymas`, plus ~50 of the 66 `censo_municipios` columns in
  `municipioDetailHandler` (`vph_*`,
  `pder_*`, religion, language, migration, education). EIC gives PEA,
  PSINDER, age groups and `vph_*` as percentages only: absolutes must be
  derived (`PCN_PEA × P_12YMAS / 100`) or taken from the tabulados.

## 5. Options (ruling: (b), staged)

**(a) Load EIC at 2,478; views roll the 9 new keys into their 2020 parents.**
Nothing joining `censo_municipios` breaks; valid only for absolute counts
(percentages need population-weighted rollups, MOE/CV rows cannot be
summed); two-parent cases forced to one parent; the 9 areas' DENUE / CLUES /
SESNSP / CE rows stay orphaned unless every layer gets the same rollup;
new-municipio detail lost.

**(b) Load as-is; extend the canonical universe to 2,478 with a bridge table.**
Most faithful, matches DENUE / CLUES / SESNSP / CE 2024. Every 2020-sourced
join (Censo, CONEVAL, CNBV panorama, SICT) returns NULL for the 9 unless a
parent fallback is applied through the bridge; `mun_polygons` (MG 2020) has
no geometry for them until MG 2025 is loaded; `locustMuniSql` and
`municipioDetailHandler` need a driving universe other than
`censo_municipios`; parents' 2020 values stay inflated for their 2025
territory.

**(c) Hold until MG 2025 geometry is loaded.** Nothing changes now; the
orphaning in §3 persists; MG 2025 is a 2.9 GB download (under the 20 GB
bulk-transfer line, but a deliberate operator call); afterwards it becomes
(b) with polygons and still needs the 2020→2025 crosswalk.

**Recommendation: (b), staged.** Step 1 = bridge table `municipio_bridge`
(cve_mun_2025, cve_mun_2020_parent, one row per pair, `nom_mun_2025`) +
canonical view `municipios_2025` (2,478) with parent-fallback columns for
Censo/CONEVAL flagged `inherited_from_parent`, and the two drivers switched
to it. That alone fixes §3 for the 4,950 orphaned DENUE rows. Step 2 = EIC
loader (open-data CSV, `eic_2025_municipio` typed view, Valor estimator only
in the main view; MOE in a sibling). Step 3 = MG 2025 polygons alongside
2020 (separate ruling on the 2.9 GB pull).

**Step 1 implemented** (apply order: migration 027 live FIRST, then restart the service, then any loader, because `CENSO_VIEWS` now asserts the view exists; drivers switched: municipios, municipio-detail, locust-muni, risk-summary MV+live, mortality-summary MV+live, risk/mortality trend meta, layers/values muni keys) (migration
`scripts/migrations/027-municipio-bridge-2025.sql`, canonical DDL in
`scripts/migrate-censo-views.sql`):

- `municipio_bridge_2025`: 11 (child, parent) rows for the 9 keys, one per
  pair, with `nom_mun_2025` (EIC spelling), `nom_mun_2020_parent`
  (`censo_municipios` spelling) and `decreto`.
- `municipios_2025`: 2,478 rows / 2,478 keys = the 2,469 `censo_municipios`
  rows plus the 9, all Censo columns, `is_new_2025` and
  `parent_cve_mun_2020 text[]` (1–2 parents; empty for the 2,469). The 9
  get `nom_mun`, `entidad`, `mun` and `nom_ent` (from `censo_entidades`);
  every Censo value is NULL. Unlike the recommendation above, nothing is
  inherited from the parent: a parent's 2020 figures describe the
  pre-split territory, and the parent keeps reporting them, so a copied
  value would count the same people twice and look like a measurement.
- `/analytics/locust-muni` and `/analytics/municipio-detail` drive from
  `municipios_2025` (the 9 appear / return 200 with NULL census fields);
  `/analytics/municipios` joins it for `nom_mun` / `pobtot`. Grants:
  `denue_sage` + `denue_api`; `load-censo.ts` drops and recreates the view
  with the censo views.
